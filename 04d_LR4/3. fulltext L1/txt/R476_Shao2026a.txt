ABSTRACT
Intelligent agent assistants are becoming essential for efficient interaction in safety monitoring digital twin (DT) 
systems. However, their deployment in small- and medium-scale hydropower projects remains limited by 
complex modules, inefficient interaction, and constrained computing resources. To bridge this gap, this paper 
proposes a lightweight agent assistant for DT systems that integrates graph retrieval-augmented generation 
(GraphRAG)-enabled task-oriented context construction with Gemma-based large language model (LLM) 
response generation. Graph-constrained automatic speech recognition (ASR) correction improves intent recog -
nition and hands-free operation. Additionally, a conflict resolution and dynamic update strategy supports 
lightweight knowledge graph (KG) maintenance. Ultimately, field validation in a practical medium-scale hy -
dropower project DT system demonstrates that the agent assistant reduces users' operational cognitive load and 
ensures response accuracy. As a result, this paper provides a lightweight, low-cost, and portable DT interaction 
solution for safety monitoring and intelligent management in resource-constrained hydropower projects, while 
supporting human-machine collaboration in DT systems.
1. Introduction
In recent years, development of hydropower project safety moni -
toring DT systems has made significant advancements in terms of high- 
fidelity visual rendering and fusion of multi-source data [1] . A hydro -
power project is defined as an integrated system for water retention, 
water conveyance, power generation, and discharge regulation. It 
mainly consists of the reservoir, dam, spillway, intake structure, water 
conveyance structures, powerhouse, tailrace, slopes, and associated 
monitoring facilities [2] . The schematic of a hydropower project is 
illustrated as Fig. 1 . Safety monitoring in hydropower projects is an 
undeniable necessity for the timely detection of abnormal structural 
characteristics, slope instability, or equipment malfunction. These 
problems may threaten structural safety, downstream communities, 
power-generation reliability, and the surrounding environment [3] .
On the basis of the general concept of DT as virtual representations of 
physical systems supported by data connection, model updating, and 
decision-support functions [4,5] , in this study, a hydropower project 
safety monitoring DT system is defined as a data-model-knowledge- 
integrated cyber-physical system that links the physical hydropower- 
station project with its virtual counterpart. It supports real-time state 
representation, monitoring analysis, safety assessment, early warning, 
and operational decision-making [6] . The development of these systems 
is critical to guarantee the high-efficiency and reliable operation of 
hydropower projects. Various functions of the system have been devel -
oped for a broad range of applications, such as safety monitoring in -
formation management, 2D and 3D integrated visualization, 
comprehensive monitoring analysis, safety assessment, early warning 
management, and so on [7,8] . According to recent studies, the core 
functions of hydropower-station safety monitoring DT systems are 
summarized in Fig. 2 .

As a result, the complexity of the system functional architecture has 
limited system adoption in daily applications [20,21] . Specifically, a 
significant mismatch exists between current interaction paradigms and 
increasingly intricate system functionalities, thereby constraining 
application efficiency. Traditional graphical user interfaces (GUIs) 
mainly rely upon the WIMP (Windows, Icons, Menus, Pointer) meta -
phor, which imposes a high cognitive load and requires extensive 
operational proficiency [22] . Accordingly, the primary challenges of the 
system function application lies in inefficient information retrieval and 
navigation bottlenecks. Traditional interaction modes impose high 
cognitive loads and steep learning curves, while lacking intuitive, nat -
ural language-based control capabilities, making it difficult to meet on- 
site demands for immediate response. The inadequacy of intelligent 
Human-Computer Interaction (HCI) remains a significant bottleneck in 
the development of digital twin fidelity and the evolution of the system 
maturity level [23,24] . Therefore, constructing an agent assistant 
equipped with intelligent human-computer interaction capabilities and 
rapid response mechanisms holds scientific significance for overcoming 
current application bottlenecks of safety monitoring DT system. In this 
study, an agent assistant refers to an execution-capable intelligent 
interface embedded in the DT system, which supports three core func -
tions: instruction execution, information response, and information 
retrieval and visualization. Specifically, it is designed to understand user 
intent, retrieve domain knowledge, invoke valid system functions, and 
present relevant information within the DT system [25,26] .
To date, in other research domains, the evolution of agent-based 
technology has provided a novel paradigm for achieving intelligent 
interaction and substantial progress has been made. Meng [27] and 
Motlaghzadeh et al. [28] have utilized game-theoretic approaches to 
model stakeholder interactions in ecological governance and climate 
adaptation. Bahrami et al. [29] and Aydin & Keles ¸ [30] integrated 
evolutionary algorithms to optimize resource allocation and supply 
scheduling under uncertainty. However, despite their efficacy in specific 
scenarios, these traditional multi-agent systems (MAS) heavily rely on 
predefined rules and fixed strategic frameworks. This reliance on 
deterministic logic limits their practical applicability in complex system 
operation. In an effort to transcend the rigidity of conventional rule- 
based approaches, the convergence of LLMs and Retrieval-Augmented 
Generation (RAG) has become a hot issue in enabling intelligent sys -
tem interaction [31,32] . Specifically, this paradigm leverages LLMs to 
provide agents with robust semantic comprehension and dynamic 
reasoning, and combines with RAG to ensure the factual consistency and 
operational accuracy of the system. For example, question answering 
(QA) systems, serving as the cornerstone of intelligent human-machine 
interaction, have undergone rapid technological development. The 
integration of LLMs and RAG has been widely utilized in optimizing 
interaction efficiency [33,34] , demonstrating early efficacy in sectors 
like e-commerce [35] and healthcare [36,37] . Notably,

GraphRAG [51,52] . However, a critical gap still remains in their prac -
tical deployment for hydropower project safety monitoring. Existing 
GraphRAG-based agent systems are typically resource-intensive and

To address these questions, this paper proposes a lightweight, 
multimodal agent assistant specifically designed for DT-based safety 
monitoring. The specific contributions are as follows: 
(1) By leveraging the Gemma LLM and incorporating domain- 
specific operational logic and professional knowledge, a system- 
function-oriented knowledge graph (SFOKG) is constructed to 
explicitly represent executable system functions, domain entities, 
and operational logic. A conflict-resolution-based incremental 
update strategy is further proposed to support lightweight dy -
namic maintenance of the KG, avoiding full graph reconstruction 
and service interruption during field deployment. This design is 
particularly suitable for small- and medium-scale hydropower

and technical support.
(2) On the basis of SFOKG, a lightweight GraphRAG-enabled agent

cognition-execution loop, enabling the agent assistant to 
reliably translate user intents into valid system commands and

Meanwhile, the proposed framework effectively mitigates hallu -

(3) With the aim of enhancing the multimodal perception and

concepts in the SFOKG, thereby preventing invalid command 
triggering. (4) The proposed agent assistant is deployed in a real 
DT safety monitoring system, demonstrating improved response 
efficiency and retrieval accuracy, as well as reduced user burden 
in complex workflows. As a result, a new paradigm of efficient 
human-machine synergy in DT system is provided. The results 
further demonstrate that the proposed method has strong prac -
tical potential for lightweight deployment and application in 
small- and medium-scale hydropower projects.

2.1. Overall system architecture and functionality
In terms of technical architecture, the digital twin-based hydropower 
project safety monitoring system can be organized into five hierarchical 
layers: the information infrastructure layer, the data resource layer, the 
system service layer, the API interface layer, and the application pre -
sentation layer. The layered architecture effectively enhances system 
development efficiency and supports scalability and maintainability. 
The overall technical framework of the system is illustrated in Fig. 3 .
As illustrated in Fig. 3 , the architecture follows a bottom-up support 
logic and a top-down service delivery logic. Specifically, the DT-based 
hydropower project safety monitoring system is organized into five hi -
erarchical layers, namely the information infrastructure layer, the data 
resource layer, the system service layer, the API interface layer, and the 
application presentation layer. This layered design clarifies the func -
tional division of the system and improves its scalability, modularity, 
and maintainability. At the bottom, the information infrastructure layer 
provides the physical foundation for system operation, including 
monitoring and perception equipment, communication network equip -
ment, and computing and storage equipment. Built upon this founda -
tion, the data resource layer provides the underlying data and resource 
support required for upper-layer services and applications.
The system service layer provides the service support for various 
business applications within the system, enabling resource reuse across 
modules. This layer is composed of the data service layer, the founda -
tional service layer, and the business service layer. 
(1) Data service layer
This layer encompasses data reading and writing, stored procedures, 
data aggregation, file services, caching services, and data backup. By 
interfacing directly with the data resource layer, it supplies essential 
data support for both the foundational services and business services. 
(2) Foundational service layer
This layer includes identity authentication, single sign-on, exception 
handling, and utility services, providing the core logical foundation 
required by the system's basic functions. 
(3) Business service layer
This layer consists of domain-specific functional modules, including 
monitoring point management, data management, safety monitoring, 
numerical simulation, slope stability analysis, knowledge graph, risk 
analysis, rehearsal plan generation, comprehensive evaluation, and 
report generation. It also supports customized service deployment ac -
cording to operational needs. The specific functionalities implemented 
by these modules are detailed in Table 1 and support further customized 
development.
Modern hydropower project safety monitoring systems always inte -
grate specialized modules, resulting in low information retrieval effi -
ciency and heightened error rates, especially during time-critical tasks 
that require fast response. Consequently, to overcome barriers caused by 
complex functional designs, the system needs to transition from a 
traditional imperative interaction paradigm (where the user dictates 
every step via clicks) to a declarative interaction paradigm. The pro -
posed agent assistant serves as the essential human-system interface 
layer, allowing users to communicate their goals and intentions via 
natural language. This design will significantly enhance response speed, 
reduce execution errors, and promote a genuine state of human-machine 
synergy.

2.2. Scenario characteristics and design implications for small- and 
medium-scale hydropower projects
Although safety monitoring DT systems share a common technical 
foundation across hydropower projects, small- and medium-scale hy -
dropower projects present a set of operational constraints that distin -
guish them from large flagship projects and directly affect the design of 
intelligent interaction mechanisms. In practice, such projects are often 
characterized by more limited computing resources, tighter mainte -
nance budgets, and reduced availability of specialized personnel for 
long-term system operation and knowledge graph maintenance. At the 
same time, they still require timely access to monitoring information, 
engineering knowledge, warning interpretation, and function invoca -
tion in daily operation and emergency response. As a result, a practical 
tension exists between increasingly integrated DT system functionalities 
and the resource-constrained reality of field deployment.
In this scenario, the challenge lies not only in the complexity of the 
DT system itself, but also in the mismatch between complex functional 
modules and the operational capacity of end users. As shown in Table 1 , 
the DT system integrates multiple domain-specific modules, including 
data management, safety monitoring, numerical simulation, slope sta -
bility analysis, knowledge graph management, risk analysis, rehearsal 
planning, comprehensive evaluation, and report generation. For users in 
small- and medium-scale projects, many routine tasks are highly goal- 
oriented and time-sensitive, such as querying the latest monitoring 
status, locating abnormal indicators, calling specific analytical func -
tions, interpreting warning information, and switching to the relevant 
visualization view. Under conventional GUI-based interaction, these 
operations usually require multi-step navigation across different mod -
ules, which increases cognitive burden and raises the risk of operational 
errors, especially in scenarios requiring rapid response.
Therefore, the target scenario of this study calls for an agent assistant 
with several specific design requirements. First, the assistant should 
support lightweight deployment, so that it can operate under limited 
computing and maintenance conditions without relying on large-scale 
model infrastructures. Second, it should be execution-grounded, mean -
ing that natural language interaction must be reliably mapped to valid 
system functions, domain entities, and operational logic rather than 
unconstrained text generation. Third, it should provide knowledge- 
grounded information support and function guidance, so that users 
can obtain accurate project-related answers and function guidance from 
structured domain knowledge rather than from general-purpose re -
sponses alone. Fourth, it should support robust multimodal interaction, 
especially in practical environments where speech input may be noisy 
and user commands may be incomplete or ambiguous. These re -
quirements together explain why a lightweight, system-function- 
oriented agent assistant with GraphRAG-guided knowledge grounding 
is particularly needed in small- and medium-scale hydropower project 
safety monitoring DT systems.
2.3. Functional requirements of agent assistant
Based on the scenario characteristics and design implications dis -
cussed above, the core functionalities of the agent assistant for small- 
and medium-scale safety monitoring DT systems consist of three cate -
gories (as depicted in Fig. 4 ): 
(1) Instruction execution
For explicit user operational commands (e.g., “Switch to a different 
project viewpoint”), the agent assistant possesses deterministic action 
mapping capabilities. By parsing action slots and object parameters 
within natural language inputs, it directly invokes underlying APIs to 
execute user instructions. 
(2) Information response
For user queries about project specifications, monitoring status, or 
engineering interpretation (e.g., “What is the dead water level of the 
project?”), the agent assistant provides knowledge-grounded informa -
tion support. It retrieves relevant context from the SFOKG and, when 
necessary, accesses the monitoring database to obtain grounded project- 
specific information, thereby generates coherent natural language 
responses. 
(3) Information retrieval and visualization
Addressing user demands for querying real-time states or specific 
scenarios (e.g., “Show the current slope deformation cloud map”), the 
agent assistant integrates information retrieval, view navigation, and 
rendering capabilities. This enables automatic viewpoint transitions 
within the digital twin environment, dynamic chart loading, and scene 
rendering, realizing the joint visualization of monitoring data and 3D 
scenes.
The three task categories do not correspond to three isolated tech -
nical pipelines; instead, they share a unified GraphRAG-enabled cogni -
tion backbone. As depicted in Fig. 5 , the proposed agent assistant adopts 
a front-end/back-end collaborative architecture. The back end of agent 
assistant consists of three layers, namely input processing, a shared 
GraphRAG-enabled cognition backbone, and downstream task branches, 
while the DT front end is responsible for interaction, execution, and 
rendering. Specifically, after a user request reaches the back end, the 
system first performs input processing, including ASR correction and 
intent classification, and then carries out graph-constrained entity

3.1. Construction of a multimodal perception layer with graph- 
constrained ASR correction method
The multimodal perception layer serves as the critical input channel 
for human-agent interaction, primarily dedicated to parsing user- 
provided text or voice commands. The core function involves extract -
ing the user's intent and key operational instructions, integrating them 
with system state data, and relaying this context to the decision layer to 
trigger system operations. The system is engineered to support robust 
voice input, significantly enhancing the convenience and operational 
efficiency of human-computer interaction. Addressing the challenge of 
potential professional terminology misrecognition or semantic deviation 
introduced by the Automatic Speech Recognition (ASR) process, this 
study proposes a novel voice command correction method grounded in a 
domain knowledge graph constraint. Specifically, this method leverages 
the functional knowledge graph of the hydropower project safety 
monitoring system as a rigorous constraint to perform semantic 
matching and calibration on the ASR candidate results, thereby ensuring

3.2. Cognition layer construction for intent classification and high-level 
task planning
This section introduces the SFOKG construction and GraphRAG 
retrieval mechanism of the proposed agent assistant. It first describes 
how system-function knowledge is extracted, normalized, and stored as 
a graph. It then explains how the graph supports intent classification, 
local or global retrieval, and downstream task routing for response 
generation, instruction execution, and visualization.
3.2.1. Construction and clustering method of system function execution KG
To construct the system function execution KG serving the intelligent 
interactive agent assistant, this study utilizes LLM-based knowledge 
extraction aimed at efficiently transforming unstructured documenta -
tion (detailing system functions, operational logic, and implicit associ -
ations) into structured knowledge.
The key technical steps and aspects of this pipeline are detailed as 
follows: 
(1) Semantic unit segmentation and operational entity identification: 
The corpus is first segmented into semantically complete text chunks 
to optimize LLM inference efficiency. Subsequently, we designed a 
domain-specific few-shot prompting strategy to guide the LLM. As 
illustrated in Table 2 , the prompt consists of three components: (1) A 
role definition assigning the LLM as a “ hydropower project expert ” . 
(2) A schema definition explicitly listing target entity types and 
relation types. (3) A set of few-shot examples covering typical edge 
cases. This structure ensures the LLM precisely identifies core en -
tities such as functional modules and critical monitoring parameters 
while concurrently generating their normalized node attributes.
(2) Operational logic relation and dependency extraction: Building 
upon entity identification, the LLM further extracts structured se -
mantic relations. We emphasize both the hierarchical “ Contains ” 
relations in the system structure and the logical correlations in 
function invocations. Accordingly, we extract functional de -
pendencies, action-object associations, and operational sequences 
and represent them as triples (entity-relation-entity) to explicitly 
map the system call logic.
For instance, given the instruction “ Enable the contour map in data 
display mode, ” the model not only extracts the entities but also con -
structs a hierarchical triplet: (Data Display, Contains, Show Contour 
Map). This structured output directly corresponds to the topological 
structure of the knowledge graph, ensuring that the agent accurately 
comprehends the subordination relationships and invocation paths of 
system functions. In parallel, for domain-specific queries, the model 
extracts semantic dependencies to support knowledge reasoning. Taking 
the aforementioned query regarding monitoring instruments as an 
example, the model constructs the relational triplet: (Slope Deformation, 
Monitored_By, Monitoring Instruments). Leveraging this topological 
structure, the system performs multi-hop retrieval within the KG to 
precisely locate specific device nodes such as “ Inclinometer ” , “ GNSS ” 
and “ machine vision ” . Consequently, it generates an accurate response 
stating, “ Slope deformation monitoring instruments include: Inclinom -
eter, GNSS and machine vision ” . This structured mapping mechanism 
ensures that the intelligent agent is capable of not only executing 
operational instructions but also conducting professional domain-

3.2.2. Knowledge graph retrieval and augmented generation
To enable the robust inference of complex instructions and guarantee 
execution accuracy, the agent assistant employs a GraphRAG-enabled 
reasoning mechanism. In the present implementation, the GraphRAG 
module is realized as a custom Python-based lightweight pipeline. 
Specifically, the SFOKG is stored in Neo4j as the graph backend, while 
Cypher queries and the Neo4j Python Driver are employed for graph 
retrieval and neighborhood traversal. Semantic embeddings are gener -
ated using BGE-M3, and community partitioning together with graph 
summarization is implemented using the Leiden algorithm via the 
igraph and leidenalg libraries. The retrieved graph context is subse -
quently routed to different downstream modules according to the 
identified task type. For information-response tasks, it is provided to the 
Gemma-3-4B large language model, which is deployed with PyTorch 
and the Hugging Face Transformers framework, for knowledge- 
grounded answer generation. For instruction-execution tasks, it is 
transformed into a standardized command payload for schema-guided 
action mapping and DT system invocation. For information retrieval 
and visualization tasks, it is further combined with monitoring data -
bases and visualization metadata to construct rendering-oriented 
outputs.
To support lightweight deployment, 4-bit quantization is adopted via 
bitsandbytes, and FastAPI is used to orchestrate the interaction among 
graph retrieval, LLM reasoning, and downstream execution modules. It 
should be noted that the SFOKG in this study was not initialized in a fully 
automatic manner. Instead, a human-in-the-loop construction strategy 
was adopted to ensure structural correctness and execution reliability in 
the safety monitoring scenario. Specifically, seed operational

tasks, it is provided to the LLM to generate a natural-language answer, 
with additional access to the monitoring database when grounded real- 
time or historical values are required. For instruction execution tasks, it 
is transformed into a standardized command payload for schema-guided 
action mapping and DT system invocation. For information retrieval and 
visualization tasks, it is further combined with monitoring databases 
and visualization metadata to construct rendering-oriented outputs, 
such as node IDs, chart requests, cloud-map parameters, or scene 
configuration instructions.
3.3. Execution layer for logic transformation and functional realization
The execution layer constitutes the final stage of the agent assistant 
and is responsible for translating the structured outputs of the cognition 
layer into three forms of downstream results: executable system com -
mands, grounded natural-language responses, and rendering-oriented 
visualization instructions. To ensure precision and reliability in high- 
stakes hydropower project safety scenarios, this layer incorporates two 
core modules: 
(1) Schema-guided action mapping (for operational tasks). Specif -
ically for control-oriented intents, this module performs the 
deterministic translation of natural language intents into 
executable system commands via a retrieval-augmented 
approach:
1) API schema retrieval: the module queries the knowledge graph to 
retrieve the specific application programming interface (API) 
schema for the target function. This schema provides strict defi -
nitions for interface names, parameter data types, and constraint 
logic.
2) Context-aware parameter extraction: based on the retrieved 
function context and the API schema, the module extracts or 
completes the required arguments (e.g., temporal ranges, device 
IDs) through schema-guided parsing and constraint checking, 
ensuring alignment with the retrieved schema structure.
3) Standardized command generation: upon validation, the module 
synthesizes a standardized command payload in JSON format (e. 
g., { “ action ” : “ set_alarm ” , “ target_id ” : “ S01 ” , “ threshold ” : 50}), 
rendering it ready for system consumption.
(2) Closed-loop interactive feedback. This module completes the 
interaction cycle by converting digital commands or text outputs 
into observable system behaviors and user confirmations:
1) Multimodal response rendering: the digital twin front-end engine 
parses the JSON payload to drive specific interface operations, 
such as navigating to monitoring scenes, isolating data on charts, 
or initiating simulation workflows. For knowledge queries, it 
renders the generated expert response in the dialogue window or 
via voice synthesis.
2) Interaction closure: to ensure operational safety, the system 
provides immediate visual or haptic feedback (e.g., a confirma -
tion dialogue for critical controls), thereby closing the loop from 
the initial voice input to the final functional execution or infor -
mation delivery.
